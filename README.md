# zoho-sprints-mcp

A remote MCP (Model Context Protocol) server that lets Claude read and manage the **StoryTrail** backlog/kanban
board in **Zoho Sprints**. Runs as a container-image AWS Lambda behind a Function URL.

## Why no Zoho Wiki support

The original goal included Zoho Wiki, but Zoho Wiki has **no current, supported REST API**. The legacy docs domain
(`apihelp.wiki.zoho.com`) now returns "Workspace not found", and there's no Wiki entry in Zoho's live
[API directory](https://www.zoho.com/developer/rest-api/). This server is Sprints-only. If you want a MCP-managed
notes/docs store later, Zoho WorkDrive has a confirmed, active REST API and would be the closest fit.

## Tools

| Tool | Purpose |
| --- | --- |
| `list_projects` | Find a project's ID (e.g. StoryTrail) |
| `get_project_metadata` | List item statuses (kanban columns), item types, priorities for a project |
| `list_sprints` | List sprints in a project |
| `list_epics` | List epics in a project |
| `list_backlog_items` | List/filter backlog or sprint items by status, epic, priority, or text search |
| `get_item` | Full item detail including comments |
| `create_item` | Create a backlog/sprint item |
| `update_item` | Edit item fields |
| `move_item_status` | Move an item between kanban columns |
| `add_comment` | Comment on an item |

Status/epic/priority/item-type parameters accept either the exact name (e.g. `"Done"`, `"Bug"`) or the numeric
Zoho ID - the server resolves names for you and calls out an ambiguous or unknown name in the error.

## Architecture

- **Node.js + TypeScript**, using the official `@modelcontextprotocol/sdk`, exposed over the streamable-HTTP
  transport in **stateless mode** (a fresh `McpServer`/transport pair per request - there's no reliable place to
  keep session state across Lambda invocations, so the SDK's serverless pattern is used).
- **AWS Lambda (container image) + Function URL**, using the
  [AWS Lambda Web Adapter](https://github.com/aws/aws-lambda-web-adapter) so the app is a completely ordinary
  Node `http.Server` (see [src/server.ts](src/server.ts)) with no Lambda-specific request/response glue code. The
  adapter proxies Function URL events to it as real HTTP calls, including response streaming
  (`invokeMode: RESPONSE_STREAM`), which a plain JSON Lambda proxy integration can't do and which the MCP
  transport's SSE responses need.
- **Function URL, not API Gateway**: Function URLs support response streaming and are simpler/cheaper for a
  single-endpoint personal tool; API Gateway would only be needed for things this doesn't require (custom
  domains via Route 53 already on that hosted zone, request validation, usage plans, etc).
- **Why Lambda, not EC2**: usage is bursty/interactive (only when you're chatting with Claude). Lambda's free
  tier (1M requests + 400,000 GB-seconds/month, permanently) makes this ~$0/month and it scales to zero when
  idle. An EC2 instance would cost money 24/7 whether or not it's used, and you'd own patching/TLS/process
  supervision yourself. The tradeoff is an occasional cold start (~1-2s) after idle, which is a non-issue for an
  interactive assistant tool.
- **Credentials in AWS Secrets Manager**, not environment variables or the repo. The Lambda's execution role can
  only `secretsmanager:GetSecretValue` on this one secret (see [infra/lib/zoho-mcp-stack.ts](infra/lib/zoho-mcp-stack.ts)).
- **CDK** (TypeScript) for infra, deployed from [infra/](infra).
- The image is built for **linux/arm64** explicitly (`Platform.LINUX_ARM64` in the CDK stack, matched to the
  Lambda's `Architecture.ARM_64`), so the same image works whether you build on Apple Silicon or CI's x86_64
  runners (via QEMU emulation in CI - see the GitHub Actions workflow).
- Startup never crashes the process: Zoho config is loaded lazily, on first `/mcp` request, and failures return a
  clear `503` instead of taking down the whole Lambda. This matters right after a fresh deploy, when the
  Secrets Manager secret exists but is still an empty placeholder.

## Security

The Function URL is public with `authType: NONE` and no request-signing (`AWS_IAM` auth) - a remote MCP client
like Claude makes plain HTTPS requests and can't do SigV4 signing. Instead, the server enforces its own bearer
token: every `/mcp` request must carry `Authorization: Bearer <token>`, where `<token>` is generated by
`scripts/oauth-setup.ts` and stored alongside the Zoho credentials in Secrets Manager. Requests without it get a
`401`. This is app-level auth, appropriate for a personal single-user integration - it is not a substitute for
proper multi-user auth if you ever expand this beyond personal use.

## Prerequisites

- Node.js 20+
- Docker (for building the Lambda container image)
- An AWS account with credentials that can create Lambda, IAM roles, Secrets Manager secrets, and CloudWatch Logs
  (the CDK stack needs `cdk bootstrap` once per account/region)
- A Zoho account on the `.com` data center (sprints.zoho.com, not `.eu`/`.in`/`.com.au`/etc.) - if you're on a
  different DC, override `ZOHO_ACCOUNTS_BASE_URL`/`ZOHO_API_BASE_URL` (see `.env.example`)

## Run locally

```bash
npm install
cp .env.example .env   # fill in ZOHO_CLIENT_ID / ZOHO_CLIENT_SECRET / ZOHO_REFRESH_TOKEN (see OAuth setup below)
npm run build
npm start               # or: npm run dev (watch) in one terminal, node dist/src/local.js in another
```

The server listens on `http://localhost:3000/mcp` (health check at `/health`).

## One-time OAuth setup

Zoho Sprints uses OAuth 2.0. This project uses Zoho's **Self Client** grant flow, since it's a personal,
single-user integration - simpler than a full authorization-code redirect flow.

```bash
npm run oauth:setup
```

The script walks you through it:

1. Register (or reuse) a **Self Client** at [api-console.zoho.com](https://api-console.zoho.com/).
2. In its "Generate Code" tab, paste in the exact scope string the script prints for you, set a duration (max
   10 minutes), and generate a grant token/code.
3. Paste that code into the script. It exchanges the code for a refresh token (which does not expire unless
   revoked), generates a bearer token for securing the `/mcp` endpoint, and:
   - pushes both into the AWS Secrets Manager secret the deployed Lambda reads from, and/or
   - writes a local `.env` file for local dev.

Re-run this script any time you need to rotate the refresh token or bearer token.

## Deploy

```bash
npm run cdk -- bootstrap   # once per AWS account/region
npm run cdk -- deploy
```

This builds the Docker image, publishes it, and creates/updates the Lambda, its Function URL, the Secrets
Manager secret (created empty on first deploy - run `npm run oauth:setup` afterwards to populate it), the log
group, and the least-privilege IAM role. On success it prints outputs including:

```
ZohoSprintsMcpStack.McpEndpoint = https://<id>.lambda-url.ap-southeast-2.on.aws/mcp
```

### CI/CD

[.github/workflows/deploy.yml](.github/workflows/deploy.yml) runs lint/typecheck/tests on every push and PR, and
deploys on push to `main`. It needs two repository secrets: `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` for
an IAM user/role with the same permissions as above. (A future improvement would be swapping these for OIDC-based
short-lived credentials instead of long-lived access keys.)

## Point Claude at the deployed server

Add it as a remote MCP connector using the `McpEndpoint` URL from the deploy output, with an `Authorization`
header of `Bearer <the MCP_API_KEY printed by oauth-setup.ts>`.

Verify it's alive:

```bash
curl -i https://<id>.lambda-url.ap-southeast-2.on.aws/mcp \
  -H "Authorization: Bearer <your-mcp-api-key>" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"test","version":"1.0"}}}'
```

A `200` with a `serverInfo` block means it's up and authenticated. A `503` with a message about missing Zoho
credentials means the Secrets Manager secret hasn't been populated yet - run `npm run oauth:setup`.

## Repo structure

```
src/
  zoho/          OAuth token management + typed Zoho Sprints API client
  mcp/tools/     One file per MCP tool group
  mcp/server.ts  Registers all tools onto an McpServer
  server.ts      Plain node:http server hosting the MCP transport (used locally and in the Lambda image)
  local.ts       Local dev entrypoint
  config.ts      Loads credentials from env (local) or Secrets Manager (Lambda)
scripts/
  oauth-setup.ts One-time interactive OAuth + Secrets Manager setup
infra/
  bin/app.ts, lib/zoho-mcp-stack.ts   CDK stack (Lambda, Function URL, secret, log group, IAM)
test/            Vitest unit tests (mocked Zoho API)
Dockerfile       Lambda container image (Lambda Web Adapter + this server)
```
